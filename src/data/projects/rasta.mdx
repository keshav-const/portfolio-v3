## The problem

Good travel knowledge about India is spread across YouTube videos, wikis, blogs and podcasts, and most of it never says where a claim came from. Rasta collects those sources and builds a graph of places and cultural entities in which **every entity links back to the evidence for it**.

## The pipeline

A Python batch pipeline runs in stages:

1. **Ingest and metadata.** Sources are collected from YouTube, Wikipedia and Wikivoyage, blogs (RSS) and podcasts.
2. **LLM gate.** A cheap model decides whether a source is worth processing before any expensive call is made.
3. **Transcripts.** YouTube transcripts are fetched; podcasts are transcribed locally with faster-whisper (CPU, int8).
4. **LLM extraction.** Entities, claims and stance are extracted as JSON.
5. **Entity resolution.** Matching tries exact names, then aliases, then fuzzy similarity with `pg_trgm`. Matches at 0.85 or above link automatically; ambiguous ones go to a review queue.
6. **Scoring.** An explicit, readable formula: `0.30·frequency + 0.20·recency + 0.20·sentiment + 0.15·authority + 0.15·depth`.

## Making LLM calls dependable

The LLM client talks to any OpenAI-compatible provider. It retries with backoff on 429 and 5xx, can pace requests, and parses JSON tolerantly, so a reply wrapped in code fences or prose doesn't break a run.

## Geocoding at speed

Places are geocoded across four providers at once (Photon, Nominatim, LocationIQ, Geoapify). Each provider runs in its own thread with its own throttle, and a miss on one provider is retried on another.

## The web app

A Next.js app, **Khoj**, sits on top: a public site with a map, an admin console for the review queue, and a developer portal for API keys. API keys are stored only as SHA-256 hashes, payment webhooks are verified with a constant-time HMAC comparison, and admin routes require a signed session cookie. The data is served by the [Khoj API](/projects/khoj-api), written in Go.
